优化点（基于当前代码状态推断）

P0

拆分摆摊域逻辑，停止继续把规则堆进 stall.gd

依据：scripts/world/stall.gd 已达 454 行，同时承担库存装载、顾客定价决策、碰撞体创建、城管检测目标、玩家空气墙和收摊回仓模拟。

预期收益：降低摆摊回归 bug 概率，后续接“许可证/执法/促销/摊位升级视觉”时更容易定位问题。

建议落点：scripts/world/stall.gd，可拆为 stall_inventory、stall_sales_policy、stall_runtime_nodes 或等价子模块。

粗略实施成本：中。

是否需要先验证：是，需要先跑现有摆摊相关测试并补一个“开摊-售卖-收摊”端到端冒烟用例。

P1

把经营数值从“功能通路”推进到“可调平衡”

依据：configs/crops.json 中多种作物已接入，但当前样本里几乎都为 growth_days = 0；系统有了，经营节奏还没有真正拉开。

预期收益：让玩家在种植、补货、摆摊、等待与收益之间出现明确取舍，避免多作物最后只是不同贴图的同一件事。

建议落点：configs/crops.json、scripts/world/farm_plot.gd、scripts/autoload/game_state.gd。

粗略实施成本：小到中。

是否需要先验证：是，建议先用固定随机种子做 3 到 5 天经营模拟。

P1

收紧资源与配置一致性校验，减少“苹果兜底”掩盖问题

依据：scripts/world/farm_plot.gd 和 scripts/autoload/config_loader.gd 在缺配置时会退回苹果资源，这能保证不中断，但也会把多作物资源缺口静默吞掉。

预期收益：更早暴露漏图、漏配置、错路径，避免后续内容扩张后出现“玩法正常但资产挂错”的隐性缺陷。

建议落点：configs/assets.json、docs/asset_registry.md、scripts/autoload/config_loader.gd、tests/generated_asset_layout_test.gd。

粗略实施成本：小。

是否需要先验证：否，可以直接先补校验脚本和失败测试。

P2

把 GameState 拆成进度、日结和农地状态子域

依据：scripts/autoload/game_state.gd 已达 333 行，既管现金/升级，也管农地、时间窗、日结、原型完成条件。

预期收益：降低跨系统副作用，后续做存档、失败条件、结算面板时不会继续扩大单例耦合。

建议落点：scripts/autoload/game_state.gd，拆出日统计或农地状态辅助对象。

粗略实施成本：中。

是否需要先验证：是，需要先梳理信号和外部调用面。

P2

补一层可开关的经营/巡逻调试日志

依据：road_navigator.gd 只有有限导航警告开关，顾客偏好决策、购买等待、城管刷点与抓捕原因目前都缺统一诊断出口。

预期收益：调平衡与复现问题会快很多，尤其是“为什么这个顾客不买”“为什么今天城管太密”这类体验问题。

建议落点：scripts/world/customer.gd、scripts/world/chengguan_spawner.gd、scripts/world/stall.gd。

粗略实施成本：小。

是否需要先验证：否。

P2

把本地测试接到 CI，避免“测试很多但回归靠手跑”

依据：仓库已有大量测试文件，但未看到 .github/workflows 里的 Godot 测试流水线。

预期收益：对最近这种高频改动节奏更有价值，尤其能卡住配置、场景结构和交互回归。

建议落点：新增 .github/workflows，并补一份测试运行说明到 docs/development_baseline.md。

粗略实施成本：中。

是否需要先验证：是，需要先确认当前测试命令和 headless 环境可稳定跑通。

新增功能建议（创意性建议，结合当前项目状态）

P1

人群需求看板：把顾客画像转成可读市场信息

依据：项目已经有 customer_preferences.json、学校/工厂/住宅等端点和多作物体系，但玩家还看不到“哪些人喜欢什么”。

预期收益：把目前隐藏在代码里的偏好系统转成策略层信息，形成“选作物 - 选时段 - 选摊点”的经营决策。

建议落点：scripts/ui/hud.gd 或新增市场情报面板，数据源来自 ConfigLoader 与日结。

粗略实施成本：中。

是否需要先验证：是，先验证玩家能否理解并利用该信息。

P1

合法摆摊/风险经营分支：把城管系统变成玩法而非惩罚动画

依据：已有警察局端点、城管巡逻、摊位影响半径和升级系统，适合自然长出“许可证、罚款、低风险摊位、高收益黑摊”机制。

预期收益：让城管不只是阻断玩家，而是推动选址、升级和资金分配的核心经营抉择。

建议落点：scripts/world/chengguan.gd、scripts/world/stall_spot.gd、configs/upgrades.json、新增许可证配置。

粗略实施成本：中到大。

是否需要先验证：是，先验证罚款频率与挫败感平衡。

P1

种子店轮换库存与节日行情

依据：GameState.refresh_seed_shop_goods()、多作物配置和顾客画像已经具备基础，但种子店与市场价格变化还不够形成经营周期。

预期收益：增强“今天该囤什么、明天该卖什么”的计划感，让日循环更像经营游戏而不是流程演示。

建议落点：scripts/world/seed_shop.gd、scripts/autoload/game_state.gd、configs/crops.json。

粗略实施成本：中。

是否需要先验证：是，先做一个轻量版价格波动表。

P2

家庭仓库与出摊备货台

依据：背包和摊位都已升级为多槽位，但玩家仍主要在“背包即全部库存”的简化模型里操作，多作物后会很快显得局促。

预期收益：增强种植、囤货、出摊准备的层次，让升级背包和升级摊位的价值更明显。

建议落点：scripts/autoload/inventory.gd、家中场景、scripts/ui/backpack_panel.gd。

粗略实施成本：中。

是否需要先验证：否，可以先做单仓库版本。

P2

镇街热力图与摊点客流提示

依据：现在已有学校、工厂、住宅、医院、公交站等端点，也有 RoadNavigator 和随机刷客，完全可以把客流差异外显。

预期收益：让“去哪里摆摊”不再只看美术摆位，而是形成真实路线选择。

建议落点：scenes/town_scene.tscn、scripts/world/town_random_customer_spawner.gd、HUD 提示层。

粗略实施成本：中。

是否需要先验证：是，先确认客流提示不会过度剧透。

P3

作物品质与施肥差异化收益

依据：施肥已进入 farm_plot.gd，但当前主要只是简单增产；这条链路很适合延伸为“品质/售价/偏好加成”。

预期收益：让种植阶段也能影响摆摊阶段，而不是只在收获数量上体现。

建议落点：configs/crops.json、scripts/world/farm_plot.gd、scripts/world/stall.gd。

粗略实施成本：中。

是否需要先验证：否。

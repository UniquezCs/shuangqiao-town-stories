  • Godot AI 插件兼容性重构继续推进：addons/godot_ai/plugin.gd 引入 logger_loader.gd 动态编译日志脚本，清理旧版 runtime/*.gd Logger 文件，避免 Godot 4.3/4.4 对 extends Logger 的启动报错。

  • scripts/world/road_navigator.gd 与 tests/road_navigator_test.gd：形成了可复用的道路路由基础设施。

  • tests/customer_demographic_profile_test.gd、tests/customer_visual_pool_test.gd：开始对“外观默认画像绑定”和“不同刷客器的素材池边界”做自动化约束。
  • assets/generated/sprites/characters/*elder*、*female* 与 assets/source/customer_demographic_variants_2026_06_02/customer_demographic_variants_report.json：顾客素材池显著扩容。
  • addons/godot_ai/runtime/logger_loader.gd、addons/godot_ai/runtime/loggers/、addons/godot_ai/utils/settings.gd：插件把日志兼容、设置判断和运行时脚本组织得更清晰。

修改内容

  • scripts/world/customer.gd 现已超过 500 行，新增了 BASE_DEMOGRAPHIC_PROFILES、外观到画像的默认映射、购买等待态和路线超时计算。
  • scripts/world/customer_spawner.gd 从“线性抖动路点”转向“调用 RoadNavigator 的随机化道路路径”，使固定通勤客流也走路网。
  • scripts/world/stall.gd 的交易接口继续向画像化决策靠拢，顾客不再只按学生/工人两种规则购买。
  • scenes/town_scene.tscn 调整了住宅/工厂等端点位置、类型、碰撞边界和随机刷客节点，说明镇街布局正在向“真实客流模拟”过渡。
  • configs/assets.json 与 docs/asset_registry.md 被持续更新，资源接入流程基本遵守当前基线。

删除或废弃内容

  • addons/godot_ai/runtime/editor_logger.gd、addons/godot_ai/runtime/game_logger.gd 及对应 .uid 已从旧路径移除，迁移到 runtime/loggers/ 目录下。
  • addons/godot_ai/handlers/animation_handler.gd 与 curve_handler.gd 在本周期 diff 中出现大段删改，反映插件内部职责正在重排。
这里更像“迁移重组”而不是最终删减。若后续继续改插件，建议优先检查工具注册、热更新、导出包和低版本 Godot 启动日志是否还有残留路径引用。

可能影响

  • 性能：TownRandomCustomerSpawner 默认脚本值仍是 300-500，虽然当前场景实例把它压到 35-55，但一旦其他场景复用默认值，可能把 NPC 密度和寻路开销直接拉高。
  • 可维护性：customer.gd 同时处理动画、移动、交易、画像、计时、交互节点创建，后续任何一个需求都容易牵动全文件。
  • 资源一致性：顾客外观池已经跨越学生/工人/中年/老年多个组合，后续如果继续接入更多商品偏好或剧情身份，单靠常量数组维护会越来越脆。
  • 插件稳定性：addons/godot_ai/plugin.gd 与 mcp_dock.gd 都处于超大文件状态，日志兼容性修复虽有进展，但回归面很广。

基于当前代码状态推断的优化建议

以下内容不是“本周期已完成的改动”，而是基于当前仓库状态得出的结构化优化建议。

P0

为随机客流建立数量上限与性能回归基线

依据：scripts/world/town_random_customer_spawner.gd 默认日刷客数仍为 300-500，而当前 scenes/town_scene.tscn 实例配置为 35-55；同时 road_navigator.gd 的候选点与最近道路点查找都依赖遍历道路数组。

预期收益：避免新场景复用默认值时出现 NPC 暴涨、路径计算频繁和帧率不可控的问题，为后续客流系统扩展建立性能护栏。

建议落点文件或模块：scripts/world/town_random_customer_spawner.gd、scripts/world/road_navigator.gd、新增性能 smoke test。

粗略实施成本：中。

是否需要先验证：需要。先在当前城镇场景记录 35/55/100 刷客量下的运行帧率和峰值 NPC 数，再决定阈值。

P1

拆分 customer.gd 的画像、移动、交易职责

依据：scripts/world/customer.gd 已达 501 行，混合了基础画像表、随机个体参数、路线推进、购买等待态、动画控制和节点动态创建。

预期收益：降低改顾客行为时的回归半径，让“顾客画像调参”和“NPC 行走/购买交互”能够独立演化，也更利于测试覆盖。

建议落点文件或模块：scripts/world/customer.gd 拆为 customer_profile、customer_motion、customer_purchase_interaction 等模块，或下沉到 Resource/辅助脚本。

粗略实施成本：中到高。

是否需要先验证：建议先验证。先列出现有对外接口，避免拆分时破坏测试场景和场景脚本绑定。

P1

把顾客画像与外观池从常量迁移为配置驱动

依据：prototype_constants.gd、customer.gd 和两个 spawner 都在维护年龄、性别、素材池、预算和偏好；这与项目“配置优先”的基线已经开始产生张力。

预期收益：新增顾客类型、新商品偏好或新素材时不必继续扩写脚本常量，策划调参和素材接入成本都会下降。

建议落点文件或模块：新增 configs/customers.json 或 configs/npc_profiles.json，接入 scripts/autoload/config_loader.gd、scripts/world/customer.gd、两个 spawner。

粗略实施成本：中。

是否需要先验证：建议先验证。需要先确认画像数据是否会继续扩展到职业、剧情身份、时间段偏好。

P2

为城镇场景建立更明确的子场景边界

依据：scenes/town_scene.tscn 已同时承载道路层、装饰层、多个端点、刷客器、空气墙、城管刷怪与场景出口；内容继续增长后会让场景编辑和 diff 审阅变重。

预期收益：把路网、端点、刷怪和边界拆成可组合子场景后，地图编辑、关卡复用和测试挂载都会更顺手。

建议落点文件或模块：scenes/town_scene.tscn，可拆为 town_route_endpoints.tscn、town_spawn_systems.tscn、town_boundaries.tscn。

粗略实施成本：中。

是否需要先验证：不需要先做原型验证，但需要先梳理当前节点路径依赖。

P2

给 Godot AI 插件的大文件补模块化和回归清单

依据：addons/godot_ai/mcp_dock.gd 2496 行、plugin.gd 1687 行，且本周期继续修改日志、设置、生命周期和调试链路。

预期收益：降低插件维护门槛，减少低版本兼容修复时的连锁回归，并让日志/调试/生命周期问题更容易定位。

建议落点文件或模块：addons/godot_ai/plugin.gd、mcp_dock.gd、utils/server_lifecycle.gd，补启动/自更新/低版本日志回归脚本。

统一日志与调试输出的项目级入口

依据：现在既有插件运行时日志链路，也有游戏侧测试场景、QC 报告 JSON 和文档说明，但主游戏脚本层缺少统一的“开发态诊断面板/日志聚合”入口。

结合当前状态的新增功能建议

以下内容是创意性功能建议，不代表仓库内已经实现；但都尽量基于现有系统和最近改动落地，而不是泛泛罗列。

P1

顾客画像驱动的“商品偏好与定价反馈”系统

依据：当前顾客已有年龄、性别、预算、商品偏好，stall.gd 已按画像判定成交；但玩家侧仍缺少把这些画像信息转化为经营策略的可见反馈。

预期收益：让“看客下菜碟”成为可学习的经营玩法，而不是隐藏随机数；也能强化小镇人群差异感。

建议落点文件或模块：scripts/world/stall.gd、scripts/ui/daily_summary_panel.gd、scripts/ui/hud.gd、昨日结算文案。

粗略实施成本：中。

是否需要先验证：建议先验证。先做简单提示词或日结统计，不必一开始就上复杂图表。

P1

按端点类型与时段变化的客流热点系统

依据：TownRandomCustomerSpawner 已支持端点权重和时间分钟表，town_scene.tscn 也有学校、工厂、住宅、公共设施等端点。

预期收益：可把“早上学校口、午后工厂门口、傍晚住宅区”的客流规律做成真实经营决策，提升场景生命力。

建议落点文件或模块：scripts/world/town_random_customer_spawner.gd、scripts/world/customer_schedule.gd、端点配置数据。

粗略实施成本：中。

是否需要先验证：需要。先验证不同热点切换会不会造成 NPC 堆积或路径拥堵。

P2

围绕客群画像的种子店/进货扩展

依据：项目已经有作物、背包、种子店、摆摊和顾客偏好，但经营闭环仍偏苹果单品；画像系统刚好提供“不同客群偏好不同商品”的扩展支点。

预期收益：把当前原型从“卖苹果”推进到“根据人群搭配货品和库存”，增强长期可玩性。

建议落点文件或模块：configs/items.json、configs/crops.json、scripts/world/seed_shop.gd、scripts/world/stall.gd。

粗略实施成本：中到高。

是否需要先验证：建议先验证。先做 2-3 个差异明显的新商品，观察日结数据变化。

P2

顾客等待、围观与错失成交的现场反馈

依据：customer.gd 已经有 waiting_for_player、购买倒计时和拒绝分支，但目前玩家感知层可能仍然偏弱。

预期收益：把“人来了但你没招呼”“价高被嫌弃”“同类顾客在旁围观”的经营压力做出来，提升临场感。

建议落点文件或模块：scripts/world/customer.gd、scripts/ui/hud.gd、反馈图标资源、可能的气泡提示。

粗略实施成本：中。

是否需要先验证：不一定。可以先用现有反馈事件和 UI 图标做轻量版本。

P3

镇街事件与城管风险联动

依据：项目已有城管、摆摊位置和客流路网，但“风险”和“收益”的时空变化还没有真正联动。

预期收益：让摆摊选址不只是找人多的地方，还要考虑巡逻、罚款和临时事件，贴合题材里的小镇生存感。

建议落点文件或模块：scripts/world/chengguan_spawner.gd、scripts/world/stall_spot.gd、scripts/ui/daily_summary_panel.gd。

粗略实施成本：中。

是否需要先验证：建议先验证。需要先确认不会把早期原型节奏拉得过重。
